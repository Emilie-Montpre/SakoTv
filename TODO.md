## Backlog — Architecture technique : sources de données (APIs)

**Décidé le 2026-08-24**, suite à la découverte que TV Time (fermé) réutilisait des bases de données publiques comme backend plutôt que de tout cataloguer soi-même : **TheTVDB** pour les séries (preuve directe trouvée : `series_id` dans l'API TV Time = ID TheTVDB brut, confirmé par le dépôt `TVTimeToTraktSync` — logique vu que TV Time a racheté TheTVDB en 2019, même maison mère) et **IMDb** pour les films. Sako TV adopte la même logique : une API spécialisée par domaine plutôt qu'une seule API généraliste pour tout.

**Mise en place faite le 2026-10-09 (Catégorie 4)** : les 5 sources sont câblées et répondent en réel. Un client minimal par source dans [src/api](src/api) (`myanimelist.ts`, `thetvdb.ts`, `omdb.ts`, `streaming-availability.ts`, `wikidata.ts`, en plus de `tmdb.ts`), clés dans `.env` (modèle dans [.env.example](.env.example), exposées par [env.ts](src/constants/env.ts)), et un script de test réel par source : `npx tsx --env-file=.env scripts/test-apis.ts` (ou avec des noms de sources à la suite). Ce n'est que la plomberie : aucune fonctionnalité de l'app n'utilise encore ces clients.

- [x] **Animés — API principale : MyAnimeList (officielle, v2)** — **plomberie faite le 2026-10-09**. Comparée en détail à AniList et Jikan (wrapper REST non-officiel de MyAnimeList) :
  - **Couverture** : MyAnimeList 30 570 entrées (la meilleure), AniList 20 691, Jikan ~25k (même base que MAL).
  - **Ce que MyAnimeList apporte en plus** : crédits complets (réalisateurs, producteurs, staff) et personnages + doubleurs détaillés — nécessaire pour la future fiche personne (voir section "Fiche détail d'une personne" plus bas), pas juste "nice to have".
  - **Authentification, résolu le 2026-10-09 : pas d'OAuth du tout.** Testé en réel : pour les lectures publiques (recherche, fiche d'un animé), le **Client ID seul** dans le header `X-MAL-CLIENT-ID` suffit. Créer l'app une seule fois sur `myanimelist.net/apiconfig/create` (type "web", non-commercial, usage "hobbyist"), mettre uniquement `EXPO_PUBLIC_MYANIMELIST_CLIENT_ID` dans `.env`. Prévoir une gestion d'erreur/repli propre dans le code (panne Jikan = cas attendu, pas une exception à ignorer).

D'où l'absence totale d'effet malgré deux tentatives et un redémarrage en bonne et due forme.
- **Fix final, purement JS (compatible Expo Go)** : au lieu de désactiver l'edge-to-edge au niveau OS (impossible dans ce contexte), un rectangle opaque (`View` en position `absolute`, hauteur = `insets.top` via `useSafeAreaInsets()`, `backgroundColor: theme.background`, `zIndex: 999`, `pointerEvents="none"`) est peint par-dessus le contenu de **toutes les pages d'un coup**, dans [_layout.tsx](src/app/_layout.tsx) (au niveau racine, pas besoin de dupliquer sur chaque écran). C'est un habillage visuel (l'app dessine toujours en edge-to-edge en dessous), pas un vrai changement de comportement système — mais le résultat visible est celui voulu. La config `app.json`/`androidStatusBar` et le `translucent={false}` runtime sont laissés en place (inoffensifs, utiles si le projet passe un jour à un build natif).
- Vérifié : `tsc --noEmit` clean, `expo export --platform android` clean. Changement JS pur (composant `View` ajouté dans le layout racine) — un rechargement classique devrait suffire cette fois, pas besoin du redémarrage complet Ctrl+C/`expo start -c` qui était nécessaire pour tester la piste `app.json` (qui s'est révélée être une impasse).
