## Fait — Statut de la barre de statut (transparence)

**Bug corrigé le 2026-08-25.** Demande d'origine du 2026-08-21 enfin clarifiée avec une capture d'écran réelle : la barre de statut Android (heure/opérateur/batterie) était **transparente avec le contenu de l'app dessiné derrière elle** (`translucent` + `backgroundColor="transparent"` dans [_layout.tsx](src/app/_layout.tsx)) — l'utilisatrice voulait au contraire une barre **opaque**, avec toutes les pages qui s'affichent en dessous, jamais derrière.

- **Premier fix (insuffisant à lui seul)** : retiré `translucent`, `backgroundColor` passé de `"transparent"` à `theme.background` dans le composant runtime `<StatusBar>` de [_layout.tsx](src/app/_layout.tsx). **Testé par l'utilisatrice après rechargement complet de l'app : toujours transparent, aucun changement visible.**
- **Cause racine trouvée après vérification de la doc versionnée Expo 54** (comme l'exige [AGENTS.md](AGENTS.md)) : Android impose maintenant le mode edge-to-edge (`android.edgeToEdgeEnabled`, déprécié mais forcé à `true`, ne peut plus être désactivé). Le vrai levier pour "pousser le contenu sous la barre" n'est **pas** le prop runtime seul — c'est **`androidStatusBar.translucent`**, une clé de config **`app.json`** (donc native/manifest), qui vaut `true` par défaut ("Defaults to true to match the iOS status bar behavior").
- **Deuxième fix, testé par l'utilisatrice avec un redémarrage complet correct (Ctrl+C, fermeture totale d'Expo Go, `expo start -c`, réouverture) : toujours transparent.** Ajout de `"androidStatusBar": { "translucent": false }` dans `app.json` + `translucent={false}` runtime — **également sans effet**, confirmé par capture d'écran (image d'arrière-plan "Biohackers" toujours visible derrière l'heure/batterie).
- **Vraie cause identifiée** : `androidStatusBar.translucent` dans `app.json` est une config **native compilée dans le thème Android au build**. **Expo Go est un binaire générique déjà compilé** — il ne peut pas appliquer cette config sans un vrai build (EAS Build/prebuild), qu'on n'utilise pas sur ce projet (Expo Go uniquement, voir contrainte SDK 54 déjà notée ailleurs). D'où l'absence totale d'effet malgré deux tentatives et un redémarrage en bonne et due forme.
- **Fix final, purement JS (compatible Expo Go)** : au lieu de désactiver l'edge-to-edge au niveau OS (impossible dans ce contexte), un rectangle opaque (`View` en position `absolute`, hauteur = `insets.top` via `useSafeAreaInsets()`, `backgroundColor: theme.background`, `zIndex: 999`, `pointerEvents="none"`) est peint par-dessus le contenu de **toutes les pages d'un coup**, dans [_layout.tsx](src/app/_layout.tsx) (au niveau racine, pas besoin de dupliquer sur chaque écran). C'est un habillage visuel (l'app dessine toujours en edge-to-edge en dessous), pas un vrai changement de comportement système — mais le résultat visible est celui voulu. La config `app.json`/`androidStatusBar` et le `translucent={false}` runtime sont laissés en place (inoffensifs, utiles si le projet passe un jour à un build natif).
- Vérifié : `tsc --noEmit` clean, `expo export --platform android` clean. Changement JS pur (composant `View` ajouté dans le layout racine) — un rechargement classique devrait suffire cette fois, pas besoin du redémarrage complet Ctrl+C/`expo start -c` qui était nécessaire pour tester la piste `app.json` (qui s'est révélée être une impasse).

**Suite corrigée le 2026-08-25, même session** : sur la Fiche ([title/[id].tsx](src/app/title/[id].tsx)) spécifiquement, l'utilisatrice voulait l'inverse pour le bouton retour — qu'il flotte **transparent directement sur l'image d'arrière-plan**, pas dans sa propre barre opaque au-dessus. Fix : le `SafeAreaView edges={['top']}` (fond opaque) qui contenait le bouton a été remplacé par une simple `View` (plus besoin d'inset manuel vu que la barre de statut n'est plus translucent globalement), et le bouton retour est passé en position `absolute` (`top: insets.top + Spacing.two`, via `useSafeAreaInsets()`) par-dessus l'image, sans fond. Appliqué aux deux états du composant (chargement et rendu complet). Import `SafeAreaView` retiré (plus utilisé dans ce fichier). Vérifié : `tsc --noEmit` clean (après régénération de `.expo/types/router.d.ts`, périmé pour une raison indépendante de ce changement), `expo export --platform android` clean.

**Dernier ajustement le 2026-08-25, même session** : une fois le rectangle opaque du fix ci-dessus en place, l'image d'arrière-plan de la Fiche démarrait bien à `y=0` mais se retrouvait **cachée/coupée** derrière ce rectangle au lieu de commencer en dessous (confirmé par capture d'écran — le haut de l'image "Biohackers" était masqué). Fix : `paddingTop: insets.top` ajouté au `contentContainerStyle` du `ScrollView` de la Fiche, pour pousser tout le contenu (dont l'image) sous la barre de statut au lieu de le laisser commencer à `y=0` et être recouvert.     - Couverture observée : 2022 uniquement (row `watch`) sur cet exemple.
  - **`tracking-prod-count-by-timeframe` — réexaminé et décodé, initialement écarté à tort.** Format : `type=month-{année}-{mois}`, `count`=nombre d'épisodes vus ce mois, `runtime`=durée totale en **secondes** (vérifié : ratio cohérent avec une durée d'épisode réaliste, ~23 min/épisode en moyenne sur l'exemple). `expires_at`=timestamp Unix (en secondes, pas en microsecondes contrairement à `comments-prod-comments`) de calcul/validité de la ligne en cache — plusieurs lignes partagent le même `expires_at` (calculées dans le même batch), les mois récents ont chacun le leur (recalculées au fur et à mesure).
